# Internationalization (i18n)

The UI ships in **English (`en`)** and **Brazilian Portuguese (`pt-BR`)**.
Locale lives in the URL as the first path segment (`/en`, `/pt-BR/relics/<id>`),
following the Next.js App Router guide (`node_modules/next/dist/docs/01-app/02-guides/internationalization.md`).
No i18n library: typed dictionaries plus a React context.

## Files

- `i18n/locales.ts` — `LOCALES`, `Locale`, `DEFAULT_LOCALE` (`en`),
  `LOCALE_NAME` (endonyms for the picker), `LOCALE_COOKIE` (`NEXT_LOCALE`),
  `LOCALE_COOKIE_MAX_AGE`,
  `hasLocale`, `matchLocale` (Accept-Language negotiation), `pathLocale`,
  `localePath`, `switchLocalePath`, `languageAlternates`. Pure, used by the
  proxy, server and client.
- `i18n/dictionaries/en.ts` — the source dictionary. `Dictionary` is
  `typeof en`, so English defines the shape.
- `i18n/dictionaries/pt-br.ts` — `ptBR: Dictionary`; a missing or extra key
  is a type error.
- `i18n/dictionary.ts` — `dictionaryFor(locale)`.
- `i18n/locale-provider.tsx` — `LocaleProvider` (client, mounted by the root
  layout; also writes the locale cookie), `useLocale()`, `useDictionary()`.
- `i18n/locale-switch.tsx` — `useLocaleSwitch()` (current locale, options,
  `change(locale)`) and `LocaleSwitch` (a `SegmentedControl` EN / PT). The
  desktop header renders `LocaleSwitch`; the compact header has no room for
  a segmented control, so it renders a 44px tile with a native `<select>`
  overlaid (same pattern as its Sort control) driven by the same hook.
- `proxy.ts` — locale redirect for unprefixed paths (see **Routing**).

## Routing

- Every page sits under `app/[lang]/` and `app/[lang]/layout.tsx` is the root
  layout: `generateStaticParams` returns `LOCALES`, so every locale is
  prerendered. It sets `<html lang>`, localized `title`/`description`,
  `canonical` and `alternates.languages` (hreflang), and calls `notFound()`
  for an unknown `lang`.
- `app/relics/[id]/[face]/route.ts` (textures) stays **outside** `[lang]`:
  assets are locale-independent and the static `relics` segment wins over
  `[lang]`. Icons (`app/icon.svg`, `favicon.ico`, `apple-icon.png`) stay at the
  app root and still apply.
- `proxy.ts` only runs on paths that need a redirect. Its `matcher` skips
  `_next/`, paths with a file extension, `/relics/<id>/<face>` (textures),
  and anything already under a locale (`/en`, `/en/…`, `/pt-BR`, `/pt-BR/…`).
  Locale pages are therefore served straight from the CDN with no function
  in front of them, which is the point: a proxy on every page would add a
  function hop to every HTML request. The matcher is a string literal, so
  adding a locale means adding it there too.
  - Everything it does match is redirected (307) to `/<locale><path>`,
    locale from the `NEXT_LOCALE` cookie, else `Accept-Language`
    (`matchLocale`: exact tag, then same language, so `pt-PT`/`pt` →
    `pt-BR`), else `en`. Old share links like `/relics/<id>` keep working
    this way.
  - Unknown first segments (`/xx`) are treated as a path, so `/xx` → `/en/xx`
    → 404 inside the layout. No `global-not-found` is needed.
- **Remembering the locale** happens on the client: `LocaleProvider` writes
  `NEXT_LOCALE` (1 year, `LOCALE_COOKIE_MAX_AGE`) in an effect whenever the
  current locale differs from the cookie, so the last locale visited wins
  the next `/` redirect. It uses the Cookie Store API (`cookieStore`;
  Biome flags `document.cookie`) and skips silently where it is missing,
  in which case `/` falls back to `Accept-Language`.
- Switching language calls `router.push` to the same path under the other
  locale (`switchLocalePath` on `usePathname()`, which Next keeps in sync
  with our `pushState`), keeping query and hash. The open drawer covers the
  header, so in practice the switch happens from the index.

## Dictionaries

- Values are strings, or functions for interpolation
  (`empty.noMatch(query)`, `summary(kind, origin, subtitle)`,
  `editor.status.*`). Because of the functions, dictionaries are imported
  directly by client code (`useDictionary()` reads the module, the provider
  only carries the locale string) rather than passed as props from the
  server. Both are small, so shipping both to the client is fine.
- Pure helpers take the dictionary as an argument instead of reading
  constants: `domainTitle(domain, dict)`, `itemSummary(item, dict)`,
  `cellValue(item, field, dict)`, `specRows(item, dict)`,
  `queryCatalog(..., dict.kind)`. Server code (metadata, OG image) uses
  `dictionaryFor(lang)` from `params`. `next/root-params` is not used:
  it does not run in the OG image route.
- Data stays as keys, labels come from the dictionary: `DOMAINS`, `SORTS`,
  `KINDS` are plain arrays; `Column.label` is a `keyof dict.columns`; spec
  rows use `keyof dict.spec`; editor fields use `dict.editor.fitField` /
  `geometryField` keyed by the field key, option choices by
  `keyof dict.editor.choice`.
- **Search** matches the kind label in the active locale.
- **Not translated**: the brand name `Relics` (`site.name`, same in every
  locale), relic data (titles, origin, mint, metal…, from
  `.relic` manifests), condition *codes* (UNC, VF… stay as stored; only the
  names in the drawer are translated, using Brazilian numismatic terms:
  Flor de cunho, Soberba, Muito bem conservada…), keyboard key names
  (`Esc`), units, `.relic` codec error messages, and the dev-only relic
  editor and its buttons (English only, kept out of the dictionaries so
  nothing of them ships to production).
- The 600 dpi template caption (`downloadTemplate(..., title)`) and the OG
  card (`/<lang>/relics/<id>/opengraph-image/card`) are localized.
  `generateImageMetadata` exists only to give the OG image a localized `alt`.

## Adding a locale

1. Add the tag to `LOCALES` and `LOCALE_NAME` in `i18n/locales.ts`.
2. Add `i18n/dictionaries/<tag>.ts` typed as `Dictionary` and register it in
   `i18n/dictionary.ts`.
3. Check the compact header and the texture editor kind picker at 390px;
   long labels there are the usual overflow.
